# Agentic Multi-Agent Orchestrator (F36)

**Maturity:** L3 Gold Standard  
**Version:** 1.0.0

A reference implementation for coordinating specialized AI agents through explicit task decomposition, capability-based routing, bounded specialist execution, critique, safety review, provenance-aware state, failure containment, and human approval.

F36 focuses on the control plane of multi-agent systems. Instead of presenting several role names around one shared prompt, it makes planning, routing, execution, review, state transitions, tool access, specialist registration, failures, and approval boundaries visible in code and testable as separate system behaviors.

The repository is intended for engineers, researchers, students, and platform teams studying or building multi-agent architectures. It is not an autonomous authority layer for consequential external actions.

## Why this repository exists

A multi-agent system introduces problems that do not appear in a single-agent workflow:

- How should a goal be decomposed into tasks?
- Which specialist is actually eligible for each task?
- What happens when several agents appear equally suitable?
- What happens when no specialist is suitable?
- How are specialist capabilities declared and enforced?
- How are tool calls bounded?
- How does one agent consume another agent's result without losing provenance?
- How are contradictions and failures represented?
- Can a failed specialist silently disappear from the final answer?
- Who has authority to approve a consequential completion?

F36 treats these as architecture problems rather than prompt-writing details.

## Core architecture

```text
user goal / workflow request
            |
            v
      Planner Agent
            |
            v
       Router Agent
            |
            v
   capability matching
            |
            v
     Execution Agent
            |
            v
  Specialist Registry
            |
            v
 selected specialist(s)
            |
            v
       Critic Agent
            |
            v
       Safety Agent
            |
            v
 automated eligibility gates
            |
            v
    explicit human approval
            |
            v
 approved workflow completion
```

The orchestrator coordinates this sequence while preserving the evidence and state generated by each stage.

## Agents

F36 contains five control-plane agents under `AGENTS/`:

| Agent | Responsibility | Core question |
|---|---|---|
| Planner Agent | Decompose the requested goal into bounded work | What tasks must be completed, and in what structure? |
| Router Agent | Match tasks to declared specialist capabilities | Which registered specialist is eligible to perform this task? |
| Execution Agent | Invoke the selected specialist and record the result | Was the selected capability actually executed successfully? |
| Critic Agent | Review workflow consistency, unresolved questions, and result quality | Does the combined workflow remain coherent and sufficiently supported? |
| Safety Agent | Review execution and approval risks | Are there blockers that should prevent progression or external action? |

The control agents do not need to perform every domain task themselves. Their purpose is to coordinate bounded specialists and make the coordination process inspectable.

## Specialist execution

`TOOLS/specialist_registry.py` is a central architectural component. Specialists are registered with declared capabilities and invoked through the execution layer rather than selected only through informal role descriptions.

Conceptually:

```text
task
  |
  v
capability requirements
  |
  v
registered specialists
  |
  +--> eligible specialist A
  +--> eligible specialist B
  +--> ineligible specialist C
  |
  v
routing policy
  |
  v
selected specialist
  |
  v
bounded invocation
```

A production implementation can extend the registry with capability schemas, versioning, permission scopes, cost limits, latency characteristics, reliability scores, jurisdiction restrictions, model requirements, and tool entitlements.

## Capability-based routing

Routing is treated as an explicit decision rather than hidden orchestration logic.

`SKILLS/routing_policy.py` provides the routing policy layer. The router scores eligible specialists against declared capabilities and is designed to block ambiguous zero-signal routing rather than guessing.

A robust routing record should preserve:

- task identifier
- required capabilities
- eligible specialists
- ineligible specialists and reasons
- routing scores or criteria
- selected specialist
- ambiguity state
- fallback or escalation state

This makes routing decisions available for evaluation and debugging.

## Task decomposition

`SKILLS/task_decomposition.py` supports the planning stage.

Good decomposition should create tasks that are:

- specific enough to route
- bounded enough to execute
- explicit about dependencies
- explicit about required evidence
- explicit about expected outputs
- independently reviewable where possible

Over-decomposition can create unnecessary coordination overhead. Under-decomposition can turn a multi-agent system back into one opaque generalist call. F36 provides a reference point for studying that tradeoff.

## Execution policy

`SKILLS/execution_policy.py` and the Execution Agent define how routed work becomes an actual specialist invocation.

Execution should preserve:

- selected specialist identity
- specialist version where applicable
- task payload
- permitted tools
- invocation status
- returned artifact or result
- failure state
- timing or execution metadata

A routing decision alone is not evidence that work occurred. F36 distinguishes routing from actual specialist invocation.

## Critique and quality review

`SKILLS/quality_review.py` supports the Critic Agent.

The critic can examine:

- whether planned tasks were actually completed
- whether specialist outputs contradict one another
- whether required evidence is missing
- whether unresolved questions remain
- whether a result is internally consistent
- whether the final synthesis overstates specialist evidence

The critic is a review layer, not a mechanism for silently rewriting failed evidence into a successful answer.

## Safety review

`SKILLS/safety_review.py` supports the Safety Agent.

Safety review occurs after execution evidence is available so it can reason about the actual workflow state rather than only the original request.

Potential blockers include:

- missing routing
- failed specialist execution
- unresolved conflicts
- unresolved questions
- missing evidence
- unsafe tool use
- approval-sensitive actions
- incomplete provenance

A human approval step cannot repair an active technical or safety blocker. Automated eligibility gates must pass first.

## Tools and control-plane infrastructure

F36 includes explicit orchestration utilities under `TOOLS/`:

```text
TOOLS/
├── agent_registry.py
├── event_bus.py
├── specialist_registry.py
├── state_store.py
└── tool_gateway.py
```

### Agent registry

Maintains the control-plane agent set and provides a clear place for agent registration rather than relying on hidden imports or ad hoc instantiation.

### Specialist registry

Maps domain capabilities to executable specialists. This is the foundation for real capability-based routing.

### Event bus

Provides an event-oriented coordination primitive. Production systems can use this pattern for asynchronous workflows, audit events, retries, subscriptions, and decoupled specialist execution.

### State store

Persists workflow state across planning, routing, execution, critique, safety review, and approval stages.

### Tool gateway

Provides a boundary between agents and tools. In production, this layer should enforce authentication, authorization, argument validation, rate limits, side-effect classification, environment restrictions, and audit logging.

## State and provenance

A multi-agent system needs more than conversational memory. It needs structured workflow state.

Useful state objects include:

- original goal
- plan
- task graph
- routing decisions
- specialist invocations
- tool calls
- specialist outputs
- evidence references
- failures
- critic findings
- safety findings
- unresolved questions
- approval eligibility
- human decision

State should preserve history rather than overwriting earlier evidence. If a task is rerouted or retried, the prior attempt should remain inspectable.

## End-to-end workflow

A typical F36 run follows this sequence:

1. Receive the requested goal.
2. Decompose the goal into bounded tasks.
3. Determine capability requirements for each task.
4. Query the specialist registry for eligible executors.
5. Apply routing policy and record the decision.
6. Block or escalate when routing is ambiguous or unsupported.
7. Invoke the selected specialist through the Execution Agent.
8. Record the actual invocation, tool activity, result, and failure state.
9. Repeat for dependent tasks as required by the plan.
10. Run critique across the accumulated workflow evidence.
11. Run safety review.
12. Apply automated completion and approval-eligibility gates.
13. Require explicit human approval for consequential completion.
14. Record the final state and provenance.

This separation makes it possible to identify whether a failure originated in planning, routing, specialist execution, tool use, synthesis, critique, safety review, or approval.

## Minimal versus complete examples

The repository includes both `examples/minimal.py` and `examples/complete.py` so readers can distinguish the essential orchestration loop from the fuller reference workflow.

When adapting F36, begin with the minimal control path, then add specialists, tools, memory, policies, and integrations incrementally. This makes it easier to preserve testability as the system grows.

## Human approval model

F36 separates automated eligibility from human authority.

The system can determine that a workflow is technically eligible for approval, but it does not treat that state as authorization to perform a consequential external action.

Conceptually:

```text
specialist execution complete
          |
          v
critic checks pass
          |
          v
safety checks pass
          |
          v
no active blockers
          |
          v
approval eligible
          |
          v
HUMAN DECISION REQUIRED
```

Human approval should be authenticated and recorded in production deployments. It should not be represented by an untrusted prompt string or a model-generated claim that approval occurred.

## Fail-closed behavior

F36 is designed to block progression when required control evidence is absent.

Examples include:

```text
PLAN INCOMPLETE
NO ELIGIBLE SPECIALIST
ROUTING AMBIGUOUS
SPECIALIST EXECUTION FAILED
TOOL FAILURE
UNRESOLVED CONFLICT
UNRESOLVED QUESTION
SAFETY REVIEW FAILED
APPROVAL NOT ELIGIBLE
HUMAN APPROVAL REQUIRED
```

The orchestrator should not fabricate a specialist result, silently choose an unsupported route, or convert an execution failure into a successful completion.

## Failure containment

Specialist failure is treated as workflow state. This allows the orchestrator to apply an explicit policy such as:

- retry the same specialist under bounded conditions
- route to an approved fallback
- request additional information
- mark the task unresolved
- stop dependent tasks
- escalate to a human

Fallback behavior should be explicit and testable. Automatic fallback should not expand permissions or bypass a failed safety condition.

## Tool safety and side effects

The Tool Gateway is the natural place to distinguish read-only tools from tools with external side effects.

A production gateway should classify operations such as:

- read/search
- create draft
- modify internal state
- send communication
- modify production system
- spend money
- execute transaction
- delete data
- change permissions

Higher-impact operations should require stronger authorization and, where appropriate, explicit human confirmation outside model control.

## Observability

A production multi-agent system should provide traces that answer:

- What plan was created?
- Why was a specialist selected?
- Which specialist actually ran?
- Which tools did it call?
- What evidence did it produce?
- What failed?
- Was anything retried or rerouted?
- What did the critic flag?
- What did the safety layer flag?
- Why was approval eligibility granted or denied?
- Who made the final human decision?

Useful trace identifiers include workflow ID, task ID, routing decision ID, specialist invocation ID, tool-call ID, evidence ID, and approval ID.

## Evaluation

F36 evaluates orchestration behavior rather than only final-response quality.

Important dimensions include:

- decomposition quality
- routing correctness
- no-route detection
- ambiguity detection
- specialist invocation fidelity
- failure containment
- tool-call provenance
- evidence preservation
- contradiction detection
- unresolved-question detection
- safety-blocker detection
- human-gate enforcement

A multi-agent system can produce a fluent final response while failing several of these control-plane requirements. F36 therefore keeps them independently measurable.

## Security boundaries

Multi-agent systems increase the number of components that can receive data or invoke tools. Production deployments should apply least privilege at every boundary.

Important controls include:

- scoped specialist permissions
- scoped tool credentials
- secret isolation
- input validation
- output validation
- network restrictions
- environment separation
- authenticated approvals
- immutable audit logs
- data classification
- retention controls

A specialist should not automatically inherit every tool available to the orchestrator.

## Extending F36

F36 is designed to be extended by registering new specialists rather than rewriting the entire control plane.

A new specialist should define:

- unique identity
- declared capabilities
- accepted input contract
- output contract
- allowed tools
- side-effect classification
- failure behavior
- timeout policy
- evidence requirements
- escalation path

Common extensions include:

- domain-specific specialist teams
- hierarchical planners
- DAG-based execution
- parallel task execution
- asynchronous event-driven agents
- dynamic capability discovery
- cost-aware routing
- latency-aware routing
- reliability-aware routing
- model-aware routing
- jurisdiction-aware routing
- specialist ensembles
- consensus or arbitration agents
- sandboxed code execution
- external workflow engines
- durable distributed state

New routing features should remain inspectable and benchmarkable.

## Design principles

1. Make the multi-agent control plane explicit.
2. Decompose work before routing it.
3. Route against declared capabilities rather than role-name intuition.
4. Distinguish routing from actual specialist execution.
5. Keep tool permissions bounded and auditable.
6. Preserve state and provenance across every stage.
7. Treat failures and contradictions as first-class state.
8. Use critique and safety review as independent control layers.
9. Fail closed when routing, execution, evidence, or approval requirements are incomplete.
10. Keep consequential authority with authenticated accountable humans.
